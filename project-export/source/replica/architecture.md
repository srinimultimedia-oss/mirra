# Independent implementation architecture

The first vertical slice uses browser-native SVG, ES modules, and local storage. This establishes the item model and direct manipulation without dependencies. It is not the production backend or a substitute for collaboration. The core model is DOM-independent and directly tested.

The device-local library now stores separate board documents and metadata, recent-open ordering, stars, spaces, and recoverable trash in a versioned snapshot. It migrates the earlier single-board key without deleting its recovery copy. Writes compare the last observed serialized snapshot before committing and preserve in-memory state if storage rejects the write. These checks detect stale tabs but are not transactional distributed concurrency. Cloud and multiuser semantics still require the planned backend. Frame parent relationships are independent model data and are reconciled by containment; groups have stable local identifiers; frame movement and duplication expand descendants before applying one transaction.

Planned production architecture: TypeScript web client; Postgres for workspace membership, board metadata, access grants, revisions, comments, records and jobs; an operation-based collaborative document layer for items; object storage for uploads; secure server sessions; authenticated realtime transport; adapters for official provider APIs and user-owned AI credentials. Database and collaboration technology require a measured prototype before final choice.

Build order: S02/S03 editing and persistence; S01 board lifecycle; S08/S09 structure and presentation; S06 identity/access and collaboration; S07 discussion/history; S10 facilitation; S11 records/views; S12 AI and S13 integrations; complete S04/S14/S15 and remaining per-feature gaps. This is order, not scope reduction.

Critical invariants: stable item ids; finite bounded geometry; no dangling connectors after deletion; atomic undo groups; serialization rejects malformed documents; server access checks on every board operation; reconnect cannot overwrite concurrent edits; private contributions must have explicit visibility semantics; uploads must be validated and isolated. Frontend role toggles never constitute authorization.

## Voting foundation — 2026-11-05
Voting is separate from board documents. `voting_sessions` holds configuration, eligible item ids, lifecycle/deadline, facilitator and create-intent digest. `voting_participants` holds one private JSON ballot per authenticated user plus a revision and done flag. `voting_mutations` will hold facilitator operation receipts. Generated migration0004 adds these tables only; foreign keys cascade from board to sessions and session-private data. A partial unique index allows one active session per board; expired sessions must be marked ended transactionally before a new active insert. Multiple drafts are allowed.

The pure voting module validates1–99 votes per person, optional one-vote-per-object, whole-number1s–7day durations and unique existing eligible objects. Current7day duration cap is an implementation limit, not a claim about Miro's maximum. Removed targets cannot receive new/increased votes, but existing allocations can be retained/reduced so users can recover budget. Votes are full replacement maps with at most99 positive entries; participant revisions will make concurrent updates atomic. `Object.fromEntries` preserves safe own identifiers without prototype assignment.

The public projection exposes only the caller's own ballot. Progress contains names/done flags; used counts are facilitator/board-owner-only. Individual allocations and other user ids stay private. Active/draft sessions omit results. Ended/expired sessions expose sorted object totals without voter identities. Projection tests do not substitute for API access checks.

Next API contract: authenticated board members of all roles may join/vote/done; owner/editor may create setups; session facilitator (while still an editor) or board owner may manage it. Every write must recheck current board permission in SQL. Participant CAS must check expected revision, session active/deadline and current board revision to prevent target-deletion races. Idempotent full-map retry may return an already matching current ballot. Start uses client session id/create digest; facilitator extend uses operation receipt plus deadline CAS. Do not expose other ballots or aggregate per-item counts before effective end. End-state derives from server time even without a write. Reuse board activity_revision for mutation invalidation, then add identity-bound voting SSE snapshots including deadline expiry; frontend UI and API tests remain G83/G84, not completed by this foundation.

## Sticky tag catalog — QA-075

Sticky tagIds reference up to8 unique catalog entries. Existing documents with no tags remain valid. Root tags changes use compare-and-swap of the catalog; independent text/item edits merge while concurrent catalog edits conflict explicitly. Deleting a catalog entry removes known bindings in the same transaction; a newly added remote reference or lock rejects the stale operation. Bulk tag actions reject all if any target is missing/locked/full. Clipboard includes only referenced definitions and merges matching normalized names while remapping colliding IDs. Rendering keeps tag metadata inside note bounds; long badge text truncates with full accessible title. Unsent rename input is kept only while its panel remains mounted, with baseline review after remote renames. No database migration; existing board document storage is used. ## Minimap — QA-076
Read-only local camera control; no document/schema/API changes. Geometry maps rotated item bounds and linked connector/freehand paths; content plus current viewport determines the projection. Drag captures that projection and scope until release/cancellation, avoiding feedback as camera position changes. Item geometry is cached by document item-array identity; viewport-only updates reuse map content during drag. Pointer click centers a location; drag preserves the initial grab offset; arrows pan by a viewport fraction (Shift full), Home/Enter/Space fit, Escape returns toggle focus. Button/M toggles are available to viewers and avoid editable input contexts. Presentation hides navigation and restores the open map after exit. Navigation layer4 sits above mobile panels; narrow toolbar wraps with an Undo gap. The100000-node projection test is not a rendered browser performance benchmark.

## Event connection lifecycle — QA-080
The server emits scoped renew metadata immediately before its normal12-poll close. ## Cloud draft backup is independent of submission — QA-081
CloudSession now owns its optional synchronous saveDraft callback. A validated local document is accepted into session memory before journal attempt; quota/security failures cannot prevent cloud submission or let a disjoint remote snapshot discard that edit. Device-backup failure appends a persistent warning to transport/conflict status and changes any kept-on-device claim to kept-only-in-this-tab. Successful cloud acknowledgement refreshes journal revision; explicit retry updates the current scoped backup without submitting a new cloud operation. Closed/read-only/account-mismatched sessions cannot write backups. The app exposes a persistent warning action and recovery section with retry/export; successful keyboard retry returns focus to Close. Cancelled/failed local backup alone does not disable online cloud saving. Reload/closed-tab recovery is unavailable when neither local backup nor cloud write succeeded; UI states this explicitly. Synthetic quota buffers and peer controls remain fixture-only and are excluded from deployment.

## Tab-scoped cloud recovery — QA-082
Board draft keys now bind account/board plus the existing claimed tab recovery identity. Independent tabs cannot overwrite each other on edits or late save acknowledgements. Payload context is validated against its key; old shared v2 keys remain readable by the default API but application startup reads only the current tab slot. Other/shared/closed-tab backups are listed for explicit read-only review and optional download; no review operation mutates or uploads a board. A fresh tab never auto-applies another slot. A duplicated tab or no-lock reload receives a non-destructive fork preserving baseline revision; originals remain untouched, and fork failure preserves original bytes. Existing same-tab matching-revision recovery remains; stale writes still conflict through CAS. Misfiled bytes positively identifying another account/board are unavailable for review and remain stored. Unparseable same-scope bytes remain explicit recovery data. The review dialog includes revision/object/text preview, starts JSON at top and returns focus on close. No database/schema/API change. Storage retention and native downloads remain separate verification work.

## Bounded JSON request parsing — QA-088
All object-body handlers in board-service and delegated voting read through cloud/lib/request-body.ts. It enforces actual4,000,000 UTF-8 bytes before decoding more input, handles split code points, rejects invalid UTF-8/interrupted streams, and validates a non-null object root before handler field access.413 denotes byte overflow;400 denotes malformed/non-object input. The reader cancels promptly without awaiting an unresponsive peer cancellation hook and releases its lock. It ignores untrusted Content-Length in favor of actual consumed bytes. No schema migration. Central UI render also keeps browser tab titles aligned with accepted local/remote board state, with dashboard title isolated (QA-089).
